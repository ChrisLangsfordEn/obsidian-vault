### Kiro Journal 
##### Researching SDD in Scrum #kiro 


Adopt spec-driven development in a traditional SCRUM team by making the spec the bridge between backlog items, design, and implementation, while keeping sprint planning, reviews, and retrospectives intact. Kiro fits well when you use it to turn user stories into living requirements.md, design.md, and tasks.md artifacts that stay version-controlled with the codebase.  
  
Operating model  
Use SCRUM for cadence and governance, and use Kiro specs for the actual feature contract. Kiro’s spec workflow formalizes requirements into user stories and acceptance criteria, then into design and tasks, which maps cleanly onto sprint-ready work. The key shift is that a story is not “ready” until the spec is complete enough to reduce ambiguity, dependencies, and rework.  
  
Team workflow  
Start each meaningful backlog item with a Kiro spec, not a prompt-first coding session. For feature work, choose Requirements-First when the behavior is clear and Design-First when architecture or non-functional constraints matter; Kiro explicitly supports both, and you can use both for the same project when needed. For bug work, use Bugfix Specs so you capture reproduction steps, current behavior, expected behavior, and unchanged behavior, which helps prevent regressions.  
  
SCRUM mapping  
SCRUM practice How Kiro fits  
Backlog refinement Turn candidate stories into draft specs with acceptance criteria and constraints  
Sprint planning Pull only stories whose specs have enough detail to estimate and execute  
Daily standup Track progress against tasks.md, not just a vague story description  
Review/demo Demo against acceptance criteria in requirements.md, then confirm design and task completion  
Retrospective Inspect spec quality, task churn, and missing constraints as process improvements  
Practical adoption  
Pilot Kiro with one team and one feature stream first, ideally work that has clear acceptance criteria and moderate complexity. Store specs in the repo so product and engineering share the same source of truth, and use version control reviews to treat spec changes like code changes. If your org already uses JIRA, Confluence, or similar tools, import or link existing requirements so you do not duplicate truth across systems.  
  
Governance rules  
Define a “spec done” checklist for sprint entry: user story phrasing, acceptance criteria, design notes, task breakdown, and explicit non-goals. Use the spec as the gate for implementation, but keep it lightweight enough that engineers can update it as understanding improves; Kiro’s workflow is meant to be iterative, with requirements, design, and tasks kept in sync. For shared platform or cross-team work, keep central reusable specs or spec fragments in a shared repository and reference them across teams.  
  
Adoption pitfalls  
Do not force every tiny story into a heavy spec; Kiro itself recommends specs for complex features, costly bugs, and work needing collaboration, while quick exploratory coding belongs in a lighter “vibe” mode. Avoid treating the spec as a one-time document, because the value comes from keeping it aligned with implementation as requirements evolve. Also avoid changing workflows mid-spec, since Kiro says you must choose Requirements-First or Design-First when creating the spec.  
  
Rollout plan  
Pick one Scrum team and one feature.  
  
Add a “spec required” rule for medium and large stories.  
  
Create a simple template for requirements, design, and tasks.  
  
Review spec quality in refinement and sprint planning.  
  
Measure impact on rework, defects, and time spent clarifying requirements.  
  
Expand to more teams once the process is stable.

Common challenges adopting Kiro in SCRUM teams and solutions  
Completed 2 steps  
The main challenges are usually not the tool itself but the process shift: teams over-specify, treat specs like one-off documents, or try to force Kiro into every small SCRUM story. The best mitigation is to reserve Kiro for medium-to-large work, keep specs version-controlled, and let them evolve with the sprint rather than freezing them upfront.  
  
Common challenges  
Story bloat and slow refinement. Teams can turn every item into a heavy spec, which makes refinement drag and creates backlog friction.  
  
Unclear acceptance criteria. SCRUM teams often think they understand the work without writing down how they will know it is done, which leads to rework.  
  
Mini-waterfall behavior. A spec can accidentally become a gated handoff if product, design, and engineering stop collaborating after “approval”.  
  
Workflow confusion. Teams may not know when to use Requirements-First versus Design-First, or they may try to switch mid-stream.  
  
Poor fit for small tasks. Using full specs for trivial fixes slows delivery and creates unnecessary ceremony.  
  
What works  
Set a spec threshold. Use Kiro for features, cross-cutting changes, risky bugs, and work with unclear acceptance criteria; skip it for tiny code changes.  
  
Keep specs lightweight. Focus on behavior, constraints, and task breakdown, not exhaustive documentation.  
  
Make specs living artifacts. Update requirements, design, and tasks as understanding changes, instead of treating the spec as a locked contract.  
  
Use the right workflow. Choose Requirements-First when the outcome is known and Design-First when architecture or non-functional constraints matter.  
  
Tie specs to sprint events. Use refinement to shape the spec, sprint planning to confirm readiness, and review to verify acceptance criteria.  
  
Team adoption issues  
A common organizational challenge is resistance to changing familiar SCRUM habits, especially when people see specs as extra overhead rather than a quality control mechanism. Another issue is role confusion: product owners, engineers, and Scrum Masters may not know who owns spec quality, updates, or approval. This is best solved by defining explicit ownership: the PO owns intended outcomes, engineers own feasibility and design quality, and the team owns keeping the spec aligned with implementation.  
  
Practical fixes  
Start with one pilot team and one feature stream.  
  
Define a “spec required” rule for medium and large stories.  
  
Add a simple readiness checklist: problem statement, acceptance criteria, constraints, design notes, tasks.  
  
Review spec quality during refinement, not after coding starts.  
  
Measure rework, spillover, and clarification churn to prove value.  
  
Good guardrails  
Do not use Kiro to replace SCRUM events; use it to improve the quality of inputs to those events.  
  
Do not require full specs for every backlog item, or the team will associate Kiro with bureaucracy.  
  
Do not let specs become stale; keep them synchronized with implementation changes.  
  
Do not confuse “spec completed” with “feature approved”; implementation still needs normal engineering and testing discipline.
